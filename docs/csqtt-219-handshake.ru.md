# CSQTT 2.1.9: изоляция ошибок подключения

Исходная версия: `amurcanov/csqtt`, commit `446293aa2e873ac5323ef6fd2316d9b81d966c11`.

## Что подтверждено

В `rust-client/session.rs::request_configuration` клиент ждёт подтверждения GETCONF
750, 1500 и 3000 мс: суммарно 5,25 секунды без учёта создания TURN-соединения.
Отсутствие ответа превращается в `FATAL_HANDSHAKE`; для потока, запрашивающего
конфигурацию туннеля, также отправляется событие ERROR с `fatal=true`.

При этом `rust-client/worker.rs::worker_loop` считает такую ошибку локальной:
планирует повторное подключение потока через 5–10 секунд. Но Android
`TunnelManager.kt` вызывает `handleCriticalError` и при событии `fatal=true`,
и при строке `FATAL_HANDSHAKE`. Поэтому оболочка может остановить весь туннель,
пока Rust-клиент собирается восстановить один поток.

Это конкретное противоречие между клиентом и Android-оболочкой. Оно не доказывает,
что любая ошибка Allocate останавливает весь клиент. На роутере Android-оболочки
нет; причина похожего отключения там требует отдельного наблюдения.

## Исправление в исходниках

Патч `router/patches/csqtt-2.1.9-handshake-isolation.patch`:

- заменяет тайм-аут на `HANDSHAKE_TIMEOUT`, без признака глобальной остановки;
- передаёт `fatal=false`, номер потока и этап `getconf`;
- сохраняет изолированное повторное подключение через 5–10 секунд;
- сохраняет критические ошибки при явном ответе сервера `DENIED`, включая
  неверный пароль, истечение доступа и несовместимость протокола;
- добавляет диагностику этапов Allocate → ChannelBind → GETCONF → READY,
  времени подключения, числа активных потоков, повторов и причин остановки клиента.

Диагностика включается переменной окружения `CSQTT_DIAGNOSTICS=1` перед запуском
бинарника. По умолчанию выключена. Она пишет только служебные поля без токенов,
хешей, паролей, адресов серверов и Device ID. Это отдельный переключатель:
включать `CSQTT_EVENTS` ради диагностики на роутере не нужно, поскольку в
оригинале он также меняет обработку закрытого stdin.

Набор патчей включён в сборку клиента `2.1.9-router.3`. Обычное обновление панели
сохраняет уже установленный бинарник CSQTT и само по себе этот патч не применяет.

## Локальная проверка

Стенд использует только loopback UDP, настоящий клиентский обмен TURN
Allocate/ChannelBind, шифрование транспорта и минимальные ответы сервера.
Доступ к VK, аккаунтам, интернет-серверам и роутеру не требуется.

Четыре сценария:

1. Allocate второго потока получает STUN 486. Первый поток остаётся READY,
   зарегистрирован в диспетчере; глобальный токен отмены не срабатывает.
2. TURN второго потока работает, но сервер не отвечает на GETCONF. Через примерно
   5,26 секунды завершается только эта сессия; первая остаётся активной.
   До исправления выдавался `fatal=true`, после — `fatal=false`.
3. Сервер отвечает `DENIED:wrong_password`. `FATAL_AUTH` и критическое событие
   сохраняются: молчание сети не приравнивается к явному отказу авторизации.
4. Сервер отвечает `DENIED:device_mismatch`. Клиент сохраняет явную причину:
   пароль привязан к другому устройству. Панель отображает эту причину в статусе
   и настройках CSQTT. Старый отказ сбрасывается после READY или нового запуска;
   текст сообщения берётся из фиксированного списка, а не из содержимого лога.

Результат локального прогона: 4 проверки изоляции, 9 проверок протокола,
29 проверок управления воркерами и 6 проверок событий прошли. Это 48 проверок
Rust-клиента; Android APK в рамках этой работы не собирался и не запускался.

Запуск после применения патчей к исходникам:

```sh
CSQTT_DIAGNOSTICS=1 cargo test --locked --manifest-path rust-client/Cargo.toml handshake_isolation_tests -- --nocapture
cargo test --locked --manifest-path rust-client/Cargo.toml protocol::tests
cargo test --locked --manifest-path rust-client/Cargo.toml worker::tests
cargo test --locked --manifest-path rust-client/Cargo.toml events::tests
```

Проверка изоляции сессий не заменяет проверку Android APK, длительный прогон
реального трафика или воспроизведение на конкретной сети. Причина потери ответа
GETCONF этим патчем не устанавливается. Контроль здоровья, подбор MTU и
автоматические перезапуски всего туннеля в эту работу не входят.
